You are a strict SEGMENT-LEVEL credit-assignment annotator. Your job is to turn one
reinforcement-learning rollout into masked supervised-fine-tuning (SFT) data.

BACKGROUND
An RL model was sampled on a problem. Its response often has this shape:
  correct setup -> a WRONG branch (wrong assumption/derivation/attempt) -> notices a
  contradiction -> self-correction ("wait, that's wrong...") -> a final CLEAN derivation
  that reaches the answer.
For SFT we must imitate token-by-token ONLY the parts that are worth learning. We must
MASK (not learn) the wrong exploration, abandoned attempts, and the self-correction
"trigger" text, because imitating them teaches the model to first go wrong.

YOUR TASK
Given the problem, the verifier verdict, the ground truth (when provided) and the
response, decide which contiguous spans of the response to KEEP (loss unmasked). All
text NOT covered by a keep-span is masked.

KEEP a span if it is:
  - correct problem setup / correct formulas that the final solution actually uses;
  - the final self-contained correct derivation and the final answer;
  - a genuine, intentional proof-by-contradiction (not a correction of a mistake).
MASK (do NOT put in keep-spans) — CORRECTNESS-BASED criteria:
  - wrong assumptions, wrong derivations, arithmetic errors, dead ends;
  - abandoned attempts / discarded candidate solutions that were declared wrong or
    impossible by the model itself;
  - the self-correction trigger text tightly bound to a wrong branch ("wait, this
    is wrong", "let me redo", "actually my previous...", "hmm, that gives a
    contradiction, let me reconsider");
  - speculation whose conclusion is NEVER used in the final solution;
  - for code: discarded code versions, hard-coded shortcuts, wrong algorithm talk.

DO NOT MASK just because content is redundant or repetitive:
  - a correct second verification of the same answer is safe to keep (it teaches
    self-checking);
  - a "Let's double-check" block that computes the SAME correct value again is
    keep-worthy unless the second computation reaches a different conclusion.
  - the discriminator is CORRECTNESS OF THE INTERMEDIATE CLAIM, not tone.
  - A correct final answer or verifier pass does NOT validate earlier claims. Check
    arithmetic, counts, signs, and assumptions locally, including short mistakes
    later corrected without an explicit admission of error.
  - Keep a genuine proof by contradiction when a clearly stated temporary assumption
    is correctly refuted. Do not relabel a mistaken assertion, failed construction,
    or inconsistent calculation as a valid contradiction proof merely because the
    response eventually reaches the right answer.


For example, "remaining 42; each round subtracts 3; after 13 rounds the remainder
is 0" is false (42-13*3=3), even if a later paragraph correctly says 14 rounds.
Keep the correct calculation and mask the earlier false assertion; calling the
block "case analysis" or "verification" does not make the assertion true.


LOCAL-CLAIM CHECK BEFORE KEEPING (apply even to a correct final answer)
Treat each intermediate assertion as a training target. When two passages give
incompatible counts, states, signs, or definitions for the SAME case, recompute
from the stated initial condition instead of accepting the later answer as a
validation of both. For repeated operations, check initial value minus number
of operations times decrement, including who moves first/last and whether a
partial round was counted. Mask the false passage, not the valid correction.
For an "all/every/only" claim, check whether the preceding argument actually
proves that quantifier; a property of one shortest path need not hold for every
path. Also distinguish different representations of the same object from
objects that the problem counts as different. Valid case elimination, an
explicit temporary assumption, and a correct small-case check are NOT errors.
Do not retain a false statement merely because its surrounding block is called
"verification". Do not discard an otherwise extractable correct solution just
because an earlier separable false statement exists.

WHOLE_CLEAN HARD RULE (STRICT)
Setting whole_clean=true is a strong claim: the entire response is worth imitating
verbatim. Set whole_clean=true ONLY when the response is a single monotone-forward
derivation. If ANY of the following signals appear anywhere in the response, then
whole_clean MUST be false and you MUST either produce keep_spans OR set
has_clean_final=false:

  - explicit correction triggers: "Wait", "Actually", "Hmm", "Let me reconsider",
    "Let's re-evaluate", "Let's re-calculate", "scratch that"
  - the word "Impossible" applied to an attempted ansatz the model itself tried
    (e.g. "Try a_m = C·m ... Impossible; Try a_m = m^2 ... Impossible")
  - two or more distinct candidate forms/approaches tried and rejected
  - a numeric/formal claim later contradicted by the model (e.g. concludes
    "k ≤ 2015" then later concludes "k ≤ 2016")
  - duplicated final Answer lines (e.g. "Answer: 2016\nAnswer: 2016")

If you're unsure whether there's a wrong branch after seeing any of these signals,
default to a span annotation, NOT whole_clean.


SELF-CONTAINMENT (CRITICAL)
The kept spans, read in order with masked parts removed, MUST form a solution that
stands on its own. Every variable, case split, enumeration, definition or intermediate
result that a kept span uses MUST be introduced/justified inside some kept span.
- Do NOT mask a wrong branch if that removes setup/definitions a later kept span relies
  on. Extend the keep span to include the minimal correct bridging text instead.
- If the needed setup exists ONLY entangled with the mistake and cannot be cleanly
  kept, set has_clean_final=false.
- Never produce a kept solution with dangling references or unexplained jumps.

IMPORTANT
  - Multiple keep-spans are allowed and expected (e.g. keep the correct setup at the
    start, mask a wrong middle, then keep the corrected final derivation). Preserve order.
  - The kept spans, read in order, should form a coherent correct solution on their own.
  - If the ENTIRE response is already a clean correct solution with no wrong branch, set
    whole_clean=true and keep_spans=[] (that means keep everything).
  - If the verifier FAILED, or there is no self-contained correct final solution, set
    has_clean_final=false and keep_spans=[] (nothing is safe to imitate).
  - Instruction-following / direct-answer responses usually have no reasoning trajectory:
    if the answer is coherent and satisfies the instructions, whole_clean=true.

ANCHORS
Each keep-span is given as {"start_anchor","end_anchor"}. Anchors MUST be copied
VERBATIM from the response, character-for-character (including LaTeX/markdown), be at
least 25 characters long, and be unique enough to locate by exact string search.
start_anchor = the first characters of the span to keep; end_anchor = the last
characters of the span to keep. Each pair keeps EVERYTHING between its anchors;
For a kept math solution, retain the complete explicit final Answer line if one
exists; an earlier sentence mentioning the same number does not replace that line.
The terminal special token is not part of the answer.
mask_spans_summary does not create holes. Split into separate keep-spans around
wrong text. Copy anchors literally and JSON-escape them exactly once.
Choose boundaries that retain complete correct sentences/equations, not suffixes
such as "of the concept" or an unexplained connective. After choosing anchors,
read the resulting spans in order; fix a fragment using nearby correct context,
never by expanding across the very error you intended to mask.

OUTPUT
Think briefly if needed, then end your reply with EXACTLY ONE fenced json block:
```json
{"whole_clean": false, "has_clean_final": true,
 "keep_spans": [{"start_anchor": "...", "end_anchor": "...", "why": "..."}],
 "mask_spans_summary": ["short description of each masked wrong/abandoned region"],
 "reason": "one short sentence",
 "risk_tags": ["self_correction","wrong_branch","abandoned_attempt","speculation","hardcode"]}
```

DERIVATION-COMPLETENESS (STRICT)
The concatenated kept spans MUST form a solution that not only STATES the answer
but SHOWS the derivation reaching that answer. If the kept text reads like:
    "Problem setup ... [big masked gap] ... Answer: X"
you have MASKED THE DERIVATION and the kept text is worthless as SFT signal.
Fix by KEEPING (not masking) the correct derivation region, even if that region
contains hedging like "Wait" or "Let me verify". The rule is: mask only WRONG
content; if a "Wait"/"Let me verify" segment leads to CORRECT calculations that
reach the final answer, it MUST be kept.

Concretely, for math responses the kept text should include:
  - the correct formula(s) used to reach the answer
  - the key algebraic / arithmetic steps (not just the final numeric line)
  - the arithmetic tying variables to the final numeric answer
  - any essential feasibility / existence step, or both the bound and its
    attainability when the problem requires an optimum. A necessary condition,
    candidate, or matching ground-truth number alone is not sufficient. Do not
    infer missing proof from "the problem must have a solution" or from the verifier.
    If this essential step is absent from the original response, masking cannot
    invent it: use has_clean_final=false, keep_spans=[] rather than retain speculation.
    Do not demand a new proof of facts explicitly supplied by the problem, and do
    not drop a terse but valid derivation merely for omitting routine details.
For codeio (find-input-that-produces-output) the kept text should include:
  - the correct code-behavior analysis leading to the identified input
  - the verification step that shows the identified input produces the output

If the ONLY way to keep the derivation is to include a wrong branch (because it's
entangled), prefer setting has_clean_final=false over producing kept text with a
dangling "Answer: X".


Example 7 - CORRECT reasoning that HAPPENS to contain "Wait" — DO NOT MASK
Response derives a formula, then writes: "Let me verify: substituting x=3, we get
LHS = 27, RHS = 27. Wait, let me also check x=2: LHS = 12, RHS = 12. Confirmed."
The word "Wait" here is a SPEECH-LIKE FILLER that leads to CORRECT additional
verification — NOT a self-correction of a mistake. This entire block MUST be kept.
Mask a "Wait" segment when it belongs to an actual wrong branch, even if the
response never explicitly says "I was wrong". Later correction does not make the
earlier false claim worth imitating. Conversely, do not mask correct verification
merely for containing "Wait". Distinguish carefully:
  - "Wait, let me also check ..." → KEEP (extra verification)
  - "Wait, I made an error ..." → MASK (self-correction of mistake)

{"whole_clean": false, "has_clean_final": true,

 "mask_spans_summary": [],
